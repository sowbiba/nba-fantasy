## 1. Contexte

Le lot L1 est en prod depuis le 2026-09-26 (front, authentification, moteur, synchros réactivées le 27/09). Trois faits changent le périmètre prévu :

- **cdn.nba.com renvoie 403** depuis le PC *et* depuis GitHub Actions, même avec des en-têtes de navigateur (vérifié le 27/09). - **La fermeture R8 n'est vérifiée que dans les actions serveur** (L1c). La base l'ignore.

## 3. L2a

### 3.1 Fermeture en base et mode correction

- **Fermeture (R8) dans le trigger `picks_validate`** : un `insert`, un `delete`, ou un `update` qui change `player_id`, `date`, `game_id` ou `is_x2`, est refusé si `now() >= nights.closing_at` de la soirée visée (ancienne et nouvelle date pour un déplacement). Erreur `P0001 night_closed`. Sans ligne `nights` pour la date, pas de contrôle de fermeture (les autres règles s'appliquent).
- **Les écritures de score ne sont jamais bloquées** : un `update` qui ne touche que `actual_score` (ou d'autres colonnes de résultat) passe toujours. C'est ce que font `daily_sync` et `local_nightly`.
- **Mode correction** : une fonction SQL `correct_pick(p_date, p_player_id, p_game_id)` (`p_player_id` null = suppression) pose `set_config('ttfl.correction', 'on', true)` pour sa transaction, puis écrit. Le trigger saute *uniquement* le contrôle de fermeture quand ce drapeau est posé ; cooldown (R3), éligibilité, unicité par soirée restent appliqués. `execute` révoqué à `anon` et `authenticated` : seule la clé service (actions serveur) l'appelle.
- **Action serveur `correctPick({ date, playerId | null })`** : `requireOwner()`, date passée de la saison en cours, soirée éligible (`nights`), appelle `correct_pick`. Le `game_id` est retrouvé côté serveur (match de l'équipe du joueur ce soir-là). Le score est recalculé par la synchro suivante ; après une suppression la soirée compte 0 (R14).
- **Front, page Picks** : chaque soirée passée de la saison (y compris les soirées sans pick) a un bouton « Corriger » : remplacer le joueur (recherche par nom), ajouter un pick, supprimer le pick (confirmation en deux temps, texte explicite « la soirée comptera 0 »). Le x2 d'une soirée passée n'est pas corrigeable dans ce lot (règle mensuelle, cas rare : correction en base à la demande).
- Les actions normales (`savePick`, `cancelPick`, `setX2`) gardent leur contrôle de fermeture côté serveur ; la base devient le garde-fou final.

### 3.2 Scores en direct via ESPN

- `engine/io/espn.py` et une route front lisent le scoreboard (`/apis/site/v2/sports/basketball/nba/scoreboard?dates=YYYYMMDD`) et le box score (`/summary?event=<id>`).
- **Correspondance des joueurs** : ESPN → `players.id` par nom normalisé (accents, suffixes Jr./III, ponctuation) + équipe ; table `espn_player_map(espn_id, player_id)` remplie au premier appariement réussi, et saisie manuelle possible pour les cas ambigus. Un joueur non apparié est ignoré (et journalisé), jamais attribué au hasard.
- **Correspondance des matchs** : date US + équipes domicile/extérieur (tricodes ESPN normalisés vers ceux de `games`, ex. `GS`→`GSW`, `NY`→`NYK`, `SA`→`SAS`, `NO`→`NOP`, `UTAH`→`UTA`, `WSH`→`WAS`).
- La route `/api/live-box-score/[gameId]` passe de cdn.nba.com à ESPN ; le score TTFL en direct est calculé avec `compute_ttfl_score` (R1), côté front par la même formule que `engine/rules/scoring.py` (miroir commenté).
- **Le score officiel du pick reste celui de stats.nba.com** (LeagueGameLog, `local_nightly`, J+1/J+2). ESPN ne sert qu'au direct et aux statuts de match.
- `daily_sync` : le calendrier ne vient plus du CDN (chargé par `local_nightly`) ; l'appel CDN est retiré au lieu de produire un avertissement à chaque passage.

### 3.3 `evening_refresh`

- Workflow GitHub, toutes les heures de 18h à 23h Paris (heures UTC ajustées au changement d'heure, comme `daily-sync.yml`). Jamais stats.nba.com.
- Contenu : blessures ESPN → P(joue) → recos du soir → plan ; statuts de match ESPN.
- **Alerte blessure** : après la mise à jour des blessures, si le joueur du pick (ou de la réservation) de la soirée du deck est `Out` ou `Doubtful` (miroir de `HARD_OUT_STATUSES`) et que la soirée n'est pas fermée, envoi d'une notification « Ton pick X est <statut>, change avant <heure de fermeture> ». Une seule par (soirée, joueur, statut) grâce à `reminders_sent`.

### 3.4 Rappels

- Tables `push_subscriptions(endpoint, keys, created_at, last_ok_at)` et `reminders_sent(night, kind, key, sent_at)` avec unicité `(night, kind, key)`. RLS : aucune lecture ni écriture anon.
- **Rappel d'oubli** : `pg_cron` toutes les 15 min appelle (via `pg_net`) la route `/api/reminders` (secret partagé en en-tête, stocké dans Vault / variable Vercel). La route envoie « Pas de pick ce soir, fermeture à HH:MM » à `closing_at − 2 h` puis `− 30 min` si la soirée du deck n'a pas de pick. Fenêtre de tolérance ±15 min ; idempotence par `reminders_sent`.
- **Notifier** : `WebPushNotifier` (VAPID, bibliothèque `web-push`, clés en variables d'environnement) et `TelegramNotifier`. Web Push d'abord ; un abonnement qui renvoie 404/410 est supprimé.
- **Front** : bouton « Activer les rappels » (réglages, depuis la PWA installée : iOS ≥ 16.4 exige l'app sur l'écran d'accueil) ; bouton « Envoyer une notification de test ». Le service worker affiche la notification et ouvre l'app sur « Ce soir » au tap.
- **Telegram** n'est mis en place que si le test push sur l'iPhone échoue (bot créé par l'utilisateur, token et chat id en variables d'environnement, jamais dans le chat).

### 3.5 Minors du front (parqués pendant L1c)

- Deck : filtrer `game_type` éligible sur la requête des matchs ; libellé « 14 prochaines soirées » cohérent avec la fenêtre réelle.
- Erreurs de requête Supabase silencieuses (`data || []`) : afficher un encart « données indisponibles » au lieu d'une page vide, sur Ce soir, Deck, Picks.
- Fiche joueur : `pending` partagé entre toutes les soirées (un bouton en cours ne désactive plus les autres).
- Dev local : `web/.env.local` pointe la prod ; documenter dans `docs/operations.md` qu'un clic en `npm run dev` écrit en prod.

## 4. L2b

### 4.1 Données 2025-26

- Corriger les deux zéros contradictoires (LeBron 06/03, Giannis 08/03, joués selon `game_logs`) : cause identifiée (date, import) avant toute correction ; correction en prod avec feu vert.
- Vérifier que `nights` peut être reconstruit pour 2025-26 (les soirées passées n'existent pas en base) : le backtest et `period_stats` 2025-26 en ont besoin.

### 4.2 Backtest et activation du plan

- `engine/jobs/backtest.py` tel que la spec §7 : rejoue la saison soir par soir depuis la base, sans appel externe, avec les données connues *la veille* de chaque soirée (pas de fuite du futur).
- Stratégies comparées : best-available S1, plan 30 j (S2), et les vrais picks de l'utilisateur. Métriques : moyenne par soirée (R14), zéros, valeur x2.
- Période : février–avril 2026 d'abord (stats complètes), puis toute la saison si l'historique le permet.
- **Activation** : le plan pilote la reco du soir seulement s'il bat le best-available sur la moyenne. Résultats présentés à l'utilisateur avant l'activation (drapeau de configuration, pas de code à changer).

### 4.3 x2 dans le plan (S3)

- Le planificateur passe à `scipy.optimize.milp` (spec §2.1) : affectation joueur/soirée + choix de la soirée x2 du mois, valeur doublée pénalisée par le risque (DNP = x2 perdu, score négatif doublé).
- Fin de mois : x2 forcé sur la meilleure option restante s'il n'est pas posé.
- Le deck et Ce soir affichent la suggestion « pose ton x2 ce soir » ; le x2 reste posé par l'utilisateur.

### 4.4 Minors du moteur et du SQL

- `period_stats.x2_used` borné par `p_until` ; `zeros`/`picks` limités aux soirées éligibles.
- Tests SQL manquants : `player_calendar ok = true`, `zeros`, bornes avril/mai et mode playoffs de `picks_x2_window`.

## 5. Tests
